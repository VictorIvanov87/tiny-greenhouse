# TG-033 — Fix responsive layout: center content on wide screens, fix toast overflow on mobile

**Type:** Bug
**Priority:** Medium
**Component:** frontend

**Goal**
Two layout issues affect users at opposite ends of the viewport spectrum. On wide monitors (≥ 1440 px) the main content area is capped at `max-w-6xl` but drifts left instead of centering because `mx-auto` is missing — the result is an asymmetric layout with a large dead zone on the right. On narrow phones (≤ 390 px) the alert toast stack is `fixed bottom-4 right-4 w-72`, which leaves only ~87 px of left margin and causes the toasts to overlap the page content at the bottom; with multiple alerts queued, the stack can grow off-screen upward. Both issues are straightforward CSS fixes with no logic changes required.

---

## Current Behavior

### 1. Content block left-aligned on wide viewports
`AppShell.tsx` line 48:
```tsx
<div className="w-full max-w-6xl text-slate-200">{children}</div>
```
`max-w-6xl` clamps the content at 1152 px, but without `mx-auto` the block is pinned to the left edge of the `<main>` area on any viewport wider than 1152 px (e.g. 1440 px, 1920 px). The sidebar is ~224 px wide, so the effective right margin is `viewport − 224 − 1152 = 544 px` at 1920 px — entirely empty.

### 2. Alert toasts overflow or overlap content on mobile
`AlertsProvider.tsx` line 115:
```tsx
<div className="fixed bottom-4 right-4 z-50 flex flex-col gap-3">
```
`AlertsProvider.tsx` line 119:
```tsx
className="w-72 border border-slate-200 bg-white text-slate-900 shadow-lg"
```
`w-72` = 288 px. On a 375 px phone, with `right-4` (16 px) the toast occupies pixels 71–375, which is 80 % of the screen width. When two or more alerts arrive simultaneously the stack grows upward with no cap, potentially obscuring the page header or the mobile navigation bar. The white (`bg-white text-slate-900`) also contradicts the app's dark shell theme.

## Expected Behavior

### 1. Content is horizontally centered on wide screens
Adding `mx-auto` centers the content block within the available `<main>` area regardless of viewport width:
```tsx
<div className="mx-auto w-full max-w-6xl text-slate-200">{children}</div>
```

### 2. Toast stack is capped, mobile-friendly, and dark-themed
- On mobile the toasts should span most of the viewport width (with generous margin) rather than overflow.
- The stack should show at most 3 toasts simultaneously; additional alerts are silently queued and appear as earlier ones are dismissed.
- The toast card should use dark shell colours consistent with the rest of the app.

```tsx
// Container
<div className="fixed bottom-4 right-4 z-50 flex max-h-[calc(100dvh-2rem)] flex-col gap-3
                 max-w-[calc(100vw-2rem)] sm:max-w-sm overflow-hidden">

// Each Toast
className="w-full border border-[#1f2a3d] bg-[#111c2d] text-slate-100 shadow-lg"
```
For the queue cap, in `AlertsProvider.tsx` change the `toasts` render slice:
```tsx

{toasts.map((alert) => (

// After
{toasts.slice(-3).map((alert) => (
```

## Scope

- Add `mx-auto` to the content wrapper in `AppShell.tsx` (one word change; affects all authenticated pages).
- Update toast container and card classes in `AlertsProvider.tsx`.
- Add `.slice(-3)` toast cap in `AlertsProvider.tsx`.

## Out of Scope

- Changing the number of toasts shown in the `AlertPanel` widget on the dashboard (separate component, unaffected).
- Adding toast animations / transitions (nice to have, separate PR).
- Responsive tweaks to the dashboard grid at intermediate breakpoints (covered separately if needed).

## Notes for Agents

- `mx-auto` on `AppShell.tsx` line 48 is the smallest possible change and is safe — `w-full` already prevents the div from collapsing below its natural width.
- The `max-h-[calc(100dvh-5rem)]` on the toast container reserves 80 px for the mobile header bar, preventing the stack from growing beneath the navigation button.
- `dvh` (dynamic viewport height) accounts for mobile browser chrome (address bar) collapsing — prefer it over `vh` for fixed bottom overlays.
- The `.slice(-3)` cap keeps the newest 3 toasts. Alerts that scroll out of view are still tracked in the `toasts` state and will appear as older ones are dismissed — no data is lost.
- The `ToastToggle` dismiss button (`onDismiss`) already calls `handleToastDismiss` which removes the entry from state, so dismissed toasts correctly free space for queued ones.
