# Ticket: Move camera uploads from local disk to Azure Blob Storage and persist image metadata

## Goal

Replace the current local-disk image upload flow for the ESP32-CAM with a production-style cloud flow:

- accept the JPEG upload from the ESP32-CAM
- upload the image to Azure Blob Storage instead of saving it in `./backend/uploads`
- persist image metadata in Firebase
- return a standard backend success envelope
- prepare the system for later Azure AI image analysis

This ticket is specifically about camera image storage and metadata persistence. It is not about AI analysis yet.

---

## Why this change is needed

The current implementation stores uploaded camera images in:

`./backend/uploads`

That was fine for local experimentation, but it is no longer the right architecture for the project.

We now want the image pipeline to match the final system direction:

`ESP32-CAM -> backend -> Azure Blob Storage -> metadata in DB -> later AI analysis`

Since the project will use Azure AI services for image analysis, Azure Blob Storage should become the canonical home for uploaded images.

---

## Current state

Already working:

- `POST /api/camera/upload` exists
- ESP32-CAM can upload JPEG snapshots to the backend over HTTP
- backend currently saves the file locally
- the frontend/backend stack is already evolving away from mock data
- telemetry ingestion is already implemented separately

We now want to replace local image storage with Azure Blob Storage.

---

## Target architecture for this ticket

For this ticket, the desired flow is:

1. ESP32-CAM uploads a JPEG to backend
2. backend validates request headers/body
3. backend uploads the binary to Azure Blob Storage
4. backend stores image metadata in Firebase
5. backend returns a standard response envelope with useful metadata

### Important

The ESP32-CAM should not upload directly to Azure Blob Storage.
The backend remains the ingestion layer.

---

## What to implement

### 1. Replace local file save with Azure Blob upload

In the existing camera upload route, remove the local-disk write as the primary storage target.

Instead:

- upload the JPEG buffer to Azure Blob Storage
- use a deterministic blob path / filename
- return metadata about the uploaded blob

Suggested blob naming format:

`camera/<deviceId>/<yyyy-mm-dd>/<deviceId>_<uptimeMs>.jpg`

This is just a suggestion. A similar clean hierarchy is acceptable.

Requirements:

- use Azure Blob Storage from the backend
- do not store images in `./backend/uploads` anymore as the main path
- keep the implementation minimal and clear

---

### 2. Persist image metadata in Firebase

After the blob upload succeeds, store image metadata in Firebase.

The exact Firebase product can follow the backend's existing direction, but the expectation is that metadata becomes queryable for the frontend.

Suggested metadata fields:

- `deviceId`
- `uptimeMs`
- `capturedAt`
- `contentType`
- `sizeBytes`
- `blobPath`
- `blobUrl` or canonical blob reference
- `storageProvider` = `"azure-blob"`
- `analysisStatus` = `"pending"`

Optional:

- `receivedAt`
- `filename`

Do not store the binary image itself in Firebase.
Only metadata.

---

### 3. Keep `POST /api/camera/upload`

Do not create a second ingestion endpoint unless there is a very strong reason.

Keep using:

`POST /api/camera/upload`

This endpoint should continue to accept:

Headers:

- `Content-Type: image/jpeg`
- `x-device-id`
- `x-uptime-ms`

Body:

- raw JPEG bytes

---

### 4. Update response schema in `src/lib/schemas.ts`

Add or update the camera upload response schema so it reflects the new Azure-based flow.

Suggested response fields:

- `deviceId: string`
- `uptimeMs: number`
- `sizeBytes: number`
- `contentType: string`
- `blobPath: string`
- `blobUrl: string` or equivalent
- `analysisStatus: string`
- `capturedAt: string`

Suggested schema names:

- `CameraUploadResult`
- `CameraUploadResultSchema`

Export both schema and inferred type, following project conventions.

---

### 5. Keep request validation strict

The route should continue to validate:

- `Content-Type`
- `x-device-id`
- `x-uptime-ms`
- non-empty JPEG body

If validation fails:

- return proper HTTP status
- return standard backend error envelope

If blob upload fails:

- return standard backend error envelope
- do not write partial or broken metadata records if possible

---

### 6. Use environment variables

Do not hardcode Azure or Firebase secrets in code.

Add or update `.env.example` with the required environment variables.

Suggested Azure Blob env vars:

- `AZURE_STORAGE_CONNECTION_STRING`
- `AZURE_STORAGE_CONTAINER`
- optionally `AZURE_STORAGE_ACCOUNT_NAME`

Suggested Firebase env vars only if needed by this repo's current setup.

Document clearly what is required.

---

### 7. Keep the code minimal and aligned with project conventions

Follow `AGENTS.md`:

- Node.js + TypeScript + Fastify
- Zod validation
- response envelope
- typed code
- one resource route file
- no unrelated refactors
- use existing helper patterns
- log unexpected errors with `req.log.error(err)`

Do not introduce unrelated architecture changes.

## Route behavior details

### Request

Headers:

- `Content-Type: image/jpeg`
- `x-device-id: esp32-cam-1`
- `x-uptime-ms: 12345`

Body:

- raw JPEG bytes

### Success response example

```json
{
	"ok": true,
	"data": {
		"deviceId": "esp32-cam-1",
		"uptimeMs": 12345,
		"sizeBytes": 12677,
		"contentType": "image/jpeg",
		"blobPath": "camera/esp32-cam-1/2026-03-27/esp32-cam-1_12345.jpg",
		"blobUrl": "https://<storage-account>.blob.core.windows.net/<container>/camera/esp32-cam-1/2026-03-27/esp32-cam-1_12345.jpg",
		"analysisStatus": "pending",
		"capturedAt": "2026-03-27T18:40:00.000Z"
	}
}
```

### Error response example

```json
{
	"ok": false,
	"error": {
		"code": "CAMERA_UPLOAD_FAILED",
		"message": "Failed to upload image to Azure Blob Storage"
	}
}
```
