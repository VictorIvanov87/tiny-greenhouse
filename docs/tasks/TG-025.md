# TG-025 — Disable RAG debug endpoint by default and gate behind explicit flag

**Type:** Security
**Priority:** High
**Component:** backend

**Goal**
The `/api/rag/search` endpoint exposes the internal vector store — anyone with a valid auth token can query all RAG training chunks, view similarity scores, and reverse-engineer the knowledge base. The current guard logic defaults to **enabled** in development, and the shipped `.env` has `RAG_DEBUG=true`. This endpoint must be disabled by default and only enabled when a developer explicitly opts in.

---

## Current Behavior

In `backend/src/routes/rag.ts` (lines 33–35):

```ts
const isDev = process.env.NODE_ENV !== 'production';
const debugEnabled =
  process.env.RAG_DEBUG === 'true' || (process.env.RAG_DEBUG !== 'false' && isDev);
```

The logic is:
- If `RAG_DEBUG=true` → enabled (regardless of `NODE_ENV`).
- If `RAG_DEBUG` is unset or any value other than `'false'` AND `NODE_ENV !== 'production'` → **enabled**.
- Only explicitly disabled when `RAG_DEBUG=false` OR when `NODE_ENV=production` and `RAG_DEBUG` is not `'true'`.

This means: in development, the endpoint is **open by default** unless you explicitly set `RAG_DEBUG=false`. The shipped `backend/.env` sets `RAG_DEBUG=true` (line 23), making it always on.

**Risk:** An authenticated user (even via mock auth) can call `POST /api/rag/search` to dump all crop knowledge chunks, embeddings metadata, and similarity scores. This leaks proprietary training data and could reveal system prompt patterns.

## Expected Behavior

- The endpoint is **disabled by default** in all environments.
- It is only enabled when `RAG_DEBUG=true` is explicitly set.
- The default value of `RAG_DEBUG` in `.env.example` is `false`.
- When disabled, the endpoint returns `403` with a clear error message (already implemented).

## Scope

- Simplify the debug check in `backend/src/routes/rag.ts` to a strict opt-in.
- Update `backend/.env.example` to set `RAG_DEBUG=false` with a comment.
- Log a warning at startup when `RAG_DEBUG=true` so operators are aware.

## Out of Scope

- Removing the debug endpoint entirely (it is useful for development).
- Adding admin-level RBAC (future concern).
- Rate limiting this endpoint (low priority since it will be off by default).

## Files to Modify (suggested)

- `backend/src/routes/rag.ts` — simplify the guard to strict opt-in.
- `backend/.env.example` — set `RAG_DEBUG=false` with an inline comment.
- `backend/src/app.ts` — (optional) log a startup warning when debug is enabled.

## Steps (Execution Plan)

1. In `backend/src/routes/rag.ts`, replace lines 33–35 with:
   ```ts
   const debugEnabled = process.env.RAG_DEBUG === 'true';
   ```
2. Update `backend/.env.example`:
   ```
   RAG_DEBUG=false   # Set to 'true' only for local debugging — exposes vector store search
   ```
3. (Optional) In `backend/src/app.ts` after routes are registered, add:
   ```ts
   if (process.env.RAG_DEBUG === 'true') {
     app.log.warn('RAG debug endpoint is ENABLED — /api/rag/search is accessible');
   }
   ```
4. Verify: start the server with `RAG_DEBUG` unset and confirm `POST /api/rag/search` returns `403`.
5. Verify: start the server with `RAG_DEBUG=true` and confirm the endpoint works.

## Acceptance Criteria

- With `RAG_DEBUG` unset or set to any value other than `'true'`, `POST /api/rag/search` returns `403 { ok: false, error: { code: 'rag_disabled' } }`.
- With `RAG_DEBUG=true`, the endpoint functions as before.
- `backend/.env.example` shows `RAG_DEBUG=false`.
- No behavioral change to any other endpoint.

## Notes for Agents

- This is a one-line logic change in the route guard — keep the diff minimal.
- Do not remove the endpoint itself; it is legitimately useful during development.
- Do not change the response schema or error codes — only the condition that gates access.
