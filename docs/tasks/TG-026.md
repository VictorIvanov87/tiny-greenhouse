# TG-026 — Wire rate-limit env vars to assistant endpoint

**Type:** Bug
**Priority:** Medium
**Component:** backend

**Goal**
The `.env` file defines `RATE_LIMIT_WINDOW` and `RATE_LIMIT_MAX` but the assistant route ignores them, using hardcoded values instead. This makes it impossible to tune rate limits without a code change and deploy — a problem during load testing, demos, or per-environment configuration.

---

## Current Behavior

In `backend/src/routes/assist.ts` (line 29):

```ts
assertRateLimit(`assist:${req.user!.uid}`, 30, 60 * 60 * 1000);
```

Both `30` (max requests) and `60 * 60 * 1000` (1-hour window in ms) are hardcoded.

Meanwhile, `backend/.env` (lines 25–26) defines:

```
RATE_LIMIT_WINDOW=3600
RATE_LIMIT_MAX=30
```

These variables are never read anywhere in the codebase. The `assertRateLimit` function in `backend/src/services/rate-limit.ts` (line 17) accepts `limit` and `windowMs` as parameters, so it already supports dynamic values — the route just doesn't pass them from env.

## Expected Behavior

- `assertRateLimit` reads `RATE_LIMIT_MAX` and `RATE_LIMIT_WINDOW` from env vars, with sensible defaults if unset.
- Changing the env vars and restarting the server changes the effective rate limits without a code change.
- Invalid env values (non-numeric, negative) fall back to defaults rather than crashing.

## Scope

- Read `RATE_LIMIT_MAX` and `RATE_LIMIT_WINDOW` from `process.env` in the assist route.
- Parse safely with fallback defaults.
- Update `.env.example` with clear documentation of the variables.

## Out of Scope

- Changing the rate-limit algorithm (sliding window is fine for v1).
- Per-route rate limits (only `/api/assist` is rate-limited today).
- Persisting rate-limit state across restarts (in-memory is fine for now).

## Files to Modify (suggested)

- `backend/src/routes/assist.ts` — read env vars and pass to `assertRateLimit`.
- `backend/.env.example` — document `RATE_LIMIT_WINDOW` and `RATE_LIMIT_MAX` with units and defaults.

## Steps (Execution Plan)

1. In `backend/src/routes/assist.ts`, before or at the top of the plugin function, parse the env vars:
   ```ts
   const RATE_MAX = Math.max(1, Number(process.env.RATE_LIMIT_MAX) || 30);
   const RATE_WINDOW_MS = Math.max(1000, (Number(process.env.RATE_LIMIT_WINDOW) || 3600) * 1000);
   ```
2. Replace the hardcoded call on line 29:
   ```ts
   assertRateLimit(`assist:${req.user!.uid}`, RATE_MAX, RATE_WINDOW_MS);
   ```
3. Update `backend/.env.example`:
   ```
   RATE_LIMIT_WINDOW=3600   # Window in seconds (default: 3600 = 1 hour)
   RATE_LIMIT_MAX=30        # Max assistant requests per window (default: 30)
   ```
4. Test: set `RATE_LIMIT_MAX=2` and `RATE_LIMIT_WINDOW=60`, restart, and confirm the 3rd request within 60s returns `429`.

## Acceptance Criteria

- With `RATE_LIMIT_MAX=5` and `RATE_LIMIT_WINDOW=60`, the 6th `POST /api/assist` call within 60 seconds returns `429` with a `Retry-After` header.
- With env vars unset, the defaults are `30` requests per `3600` seconds (same as current behavior — no regression).
- Non-numeric env values (e.g., `RATE_LIMIT_MAX=abc`) fall back to defaults without crashing the server.

## Notes for Agents

- The `assertRateLimit` function signature already accepts `limit` and `windowMs` — no changes needed in `rate-limit.ts`.
- Note: `RATE_LIMIT_WINDOW` is in **seconds** in the env but `assertRateLimit` expects **milliseconds** — multiply by 1000.
- Keep the diff focused on `assist.ts` and `.env.example` only.
