# Ticket: Add camera image upload endpoint for ESP32-CAM

## Goal

Implement a minimal backend endpoint that allows the ESP32-CAM device to upload a JPEG snapshot to the backend over HTTP.

This is the first backend step for the camera pipeline. The immediate goal is **not** Azure Blob Storage, Azure Vision, auth hardening, or database persistence. The goal is simply:

- accept a JPEG upload from the ESP32-CAM
- validate the request shape
- save the image locally on disk
- return a typed JSON response inside the standard backend envelope

This endpoint will later be used as the ingestion point before cloud storage and AI image analysis are added.

---

## Context

We already have two firmware tracks in the hardware side:

1. **Main ESP32 controller**
    - reads telemetry
    - outputs JSON with:
        - `uptime_ms`
        - `temperature_c`
        - `humidity_pct`
        - `pressure_hpa`
        - `light_lux`
        - `soil_moisture_raw` (currently placeholder)

2. **ESP32-CAM**
    - camera init works
    - manual snapshot over Serial works
    - next step is HTTP upload to backend

The camera should **not** talk directly to Azure services or Blob Storage from firmware. The backend should be the first receiver of the image.

---

## Required endpoint

Add a new route:

`POST /api/camera/upload`

This route should:

- accept a raw JPEG request body
- accept metadata through headers
- save the image into a local uploads directory
- return a success envelope with basic metadata

### Request

Headers expected:

- `Content-Type: image/jpeg`
- `x-device-id`
- `x-uptime-ms`

Body:

- raw JPEG bytes

### Response

Use the standard response envelope from the project.

Success example:

```json
{
	"ok": true,
	"data": {
		"deviceId": "esp32-cam-1",
		"uptimeMs": 12345,
		"sizeBytes": 12677,
		"filename": "esp32-cam-1_12345.jpg",
		"contentType": "image/jpeg"
	}
}
```

Error example:

```json
{
	"ok": false,
	"error": {
		"code": "INVALID_IMAGE_UPLOAD",
		"message": "Request body must be a JPEG image"
	}
}
```

## What to implement

### 1. Add Zod schemas in `src/lib/schemas.ts`

Create a response schema for the upload result.

Suggested shape:

- `deviceId: string`
- `uptimeMs: number`
- `sizeBytes: number`
- `filename: string`
- `contentType: string`

Name suggestion:

- `CameraUploadResult`
- `CameraUploadResultSchema`

Follow the repo convention: export both schema and inferred type.

---

### 2. Add a new route file

Create:

`src/routes/camera.ts`

This route should register:

`POST /api/camera/upload`

Requirements:

- keep the handler small
- validate metadata with Zod
- use the project response envelope helper
- log unexpected errors with `req.log.error(err)`

Important:

- keep this route MVP-simple
- do not add database code
- do not add Azure code
- do not introduce new runtime libraries unless absolutely necessary

---

### 3. Read raw request body correctly in Fastify

The route must handle a raw binary body (`image/jpeg`).

Claude should choose the smallest clean implementation compatible with the current Fastify stack.

Good outcome:

- raw JPEG bytes are accessible as a `Buffer`
- body length can be measured
- invalid/empty body is rejected

Avoid overengineering.

---

### 4. Validate request metadata

Validate headers with Zod.

Expected header semantics:

- `x-device-id`: non-empty string
- `x-uptime-ms`: integer-like value, coerced to number, non-negative
- `content-type`: must be exactly `image/jpeg` or at least start with `image/jpeg`

If validation fails:

- return proper error envelope
- return proper HTTP status

---

### 5. Save file locally

Save the JPEG to a local folder such as:

`uploads/`

Filename format suggestion:

`<deviceId>_<uptimeMs>.jpg`

Sanitize the device id enough to avoid unsafe filenames.
Keep the implementation simple and deterministic.

The uploads directory should be created automatically if missing.

Do **not** add Blob Storage yet.

---

### 6. Register the route in the server

Update `src/app.ts` and register the new route the same way the existing route files are registered.

Keep the existing architecture style.

---

### 7. Decide auth behavior explicitly

For now, the camera endpoint can stay unauthenticated if that is the simplest MVP path.

However, document that decision clearly in code comments or route notes, because later this endpoint will likely be protected or device-authenticated.

Do not invent a heavy auth system in this ticket.

---

### 8. Add a short README/dev note if useful

If appropriate, add a short note explaining how to test the endpoint locally with `curl`.

Example shape:

```bash
curl -X POST http://localhost:3000/api/camera/upload \
  -H "Content-Type: image/jpeg" \
  -H "x-device-id: esp32-cam-1" \
  -H "x-uptime-ms: 12345" \
  --data-binary "@/path/to/test.jpg"
```

This is optional but useful.

## Constraints

Follow the backend project conventions from `AGENTS.md`:

- Node.js + TypeScript + Fastify
- Zod validation
- response envelope everywhere
- one route per file
- use existing helpers from `lib/respond.ts`
- keep code minimal, typed, and documented
- no unrelated refactors
- no database
- no MQTT
- no sockets
- no Azure integration yet

## Acceptance criteria

This ticket is done when:

1. `POST /api/camera/upload` exists
2. it accepts a raw JPEG body
3. it validates required headers
4. it saves the image into a local uploads folder
5. it returns a valid success envelope
6. invalid input returns a valid error envelope
7. route is registered in `src/app.ts`
8. typecheck passes
9. changes are minimal and follow existing project structure
