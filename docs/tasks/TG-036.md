# Ticket: Add telemetry ingestion endpoint for main ESP32 greenhouse controller

## Goal

Implement a minimal backend ingestion endpoint that accepts telemetry from the main ESP32 greenhouse controller over HTTP.

This is the backend counterpart of the current firmware milestone. The ESP32 already produces structured JSON with environmental readings. The backend now needs an MVP endpoint that:

- accepts telemetry JSON from the device
- validates the payload with Zod
- returns the standard backend response envelope
- stores the latest samples in memory or a simple local mock-friendly structure
- exposes them in a way that fits the existing backend architecture

This ticket is about local backend telemetry ingestion, not database persistence, MQTT, sockets, alerts, or cloud integration.

---

## Context

We currently have two embedded tracks:

1. Main ESP32 controller
    - powered from the 12V adapter through a buck converter
    - reads:
        - `temperature_c`
        - `humidity_pct`
        - `pressure_hpa`
        - `light_lux`
        - `soil_moisture_raw` (currently `null`, later from ADS1115)
        - `uptime_ms`
    - already outputs a structured JSON line over Serial

2. ESP32-CAM
    - camera init works
    - snapshot upload to backend already works through `/api/camera/upload`

The next backend step is to accept telemetry from the main ESP32 in a similarly clean way.

---

## Recommended API shape

Implement one ingestion endpoint:

`POST /api/telemetry`

This route should:

- accept a JSON body from the ESP32
- validate the body with Zod
- normalize and return the accepted sample inside the standard response envelope
- keep the implementation minimal and typed

The route should be designed so that later it can evolve into:

- persistence in database
- per-device history
- alerting rules
- cloud sync

---

## Request payload

Expected JSON body:

```json
{
	"device_id": "esp32-main-1",
	"uptime_ms": 12345,
	"temperature_c": 24.29,
	"humidity_pct": 49.1,
	"pressure_hpa": 945.4,
	"light_lux": 121.67,
	"soil_moisture_raw": null
}
```

Notes:

- `soil_moisture_raw` should be allowed to be `null` for now
- all values should be validated
- `device_id` is required so the backend is not implicitly tied to a single device

---

## Response payload

Use the standard response envelope.

Success example:

```json
{
	"ok": true,
	"data": {
		"accepted": true,
		"sample": {
			"deviceId": "esp32-main-1",
			"uptimeMs": 12345,
			"temperatureC": 24.29,
			"humidityPct": 49.1,
			"pressureHpa": 945.4,
			"lightLux": 121.67,
			"soilMoistureRaw": null,
			"receivedAt": "2026-03-27T12:34:56.000Z"
		}
	}
}
```

Error example:

```json
{
	"ok": false,
	"error": {
		"code": "INVALID_TELEMETRY_PAYLOAD",
		"message": "Telemetry payload is invalid"
	}
}
```

---

## Should there be one route or multiple routes?

For now, keep it to one ingestion route:

- `POST /api/telemetry`

Do not split it into separate routes for temperature/light/humidity/etc.

Reason:

- the ESP32 already produces one coherent sample at one point in time
- the backend should receive that sample atomically
- this is cleaner for later history/analysis

If needed, Claude can also improve the existing read route shape later, but this ticket should stay focused on ingestion.

## What to implement

### 1. Add telemetry ingestion schemas in `src/lib/schemas.ts`

Add Zod schemas for:

#### Incoming telemetry payload

Suggested fields:

- `device_id: string`
- `uptime_ms: number`
- `temperature_c: number`
- `humidity_pct: number`
- `pressure_hpa: number`
- `light_lux: number | null`
- `soil_moisture_raw: number | null`

Name suggestion:

- `TelemetryIngestBody`

#### Normalized accepted telemetry sample

Suggested fields:

- `deviceId: string`
- `uptimeMs: number`
- `temperatureC: number`
- `humidityPct: number`
- `pressureHpa: number`
- `lightLux: number | null`
- `soilMoistureRaw: number | null`
- `receivedAt: string` (ISO datetime)

Name suggestion:

- `TelemetryAcceptedSample`

#### Response schema

Suggested shape:

- `accepted: true`
- `sample: TelemetryAcceptedSample`

Name suggestion:

- `TelemetryIngestResult`

Follow repo conventions:

- export both schema and inferred types

---

### 2. Add or update route file

Preferred option:

- extend the existing telemetry route file: `src/routes/telemetry.ts`

This file should support both:

- `GET /api/telemetry` (existing read route behavior)
- `POST /api/telemetry` (new ingestion route)

This is cleaner than creating a second route file for the same resource.

Requirements:

- keep handler small
- validate request body with Zod
- return standard envelope
- use existing helpers from `lib/respond.ts`
- log unexpected errors with `req.log.error(err)`

---

### 3. In-memory storage for now

For MVP, do not add a database.

The backend should keep accepted telemetry samples in a simple in-memory structure, for example:

- an array
- optionally scoped by `deviceId`

This should be just enough so that:

- `POST /api/telemetry` accepts and stores a sample
- `GET /api/telemetry` can return recent samples from memory
- the current mock architecture is not overcomplicated

If Claude thinks it is better to preserve the existing mocked `GET /api/telemetry` behavior and only store POSTed samples separately for now, that is acceptable, as long as the code stays simple and explicit.

---

### 4. Validation behavior

Validate the request body strictly.

Expected rules:

- `device_id`: non-empty string
- `uptime_ms`: integer-like, coerced to number, non-negative
- `temperature_c`: finite number
- `humidity_pct`: finite number
- `pressure_hpa`: finite number
- `light_lux`: finite number or `null`
- `soil_moisture_raw`: finite number or `null`

If invalid:

- return proper HTTP status
- return standard error envelope

---

### 5. Register no new infrastructure

Do not add:

- database
- Azure
- MQTT
- websockets
- cron jobs
- notification logic
- rules engine

This ticket is only about HTTP telemetry ingestion.

---

### 6. Auth behavior

For now, the telemetry ingestion route can stay unauthenticated if that is the simplest path for device integration.

However, make that decision explicit in code comments or route notes, because later device authentication will likely be needed.

Do not add a heavy auth flow in this ticket.

## Acceptance criteria

This ticket is done when:

1. `POST /api/telemetry` exists
2. it accepts the ESP32 telemetry JSON payload
3. it validates the payload with Zod
4. it returns the standard success envelope
5. invalid input returns the standard error envelope
6. accepted samples are stored in a minimal in-memory structure
7. route changes are registered cleanly in the existing server architecture
8. typecheck passes
9. changes are minimal and follow project conventions
